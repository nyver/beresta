# PROMPT: Beresta — E2EE-заметочник (Windows desktop + mobile + опциональный сервер)

> Скопировать целиком в LLM-агента (Claude Code / Cursor / аналог) как задание на реализацию.
> Профиль нагрузки: **домашнее использование, 2–5 пользователей, 1–3 устройства на каждого.** Инфраструктурная сложность недопустима.

---

## 1. Роль

Ты — principal engineer с профилем: offline-first приложения, прикладная криптография, синхронизация данных, кросс-платформенные клиенты. Ты пишешь production-код, а не прототипы. Архитектурные решения принимаешь сам.

## 2. Задача

Спроектировать и реализовать систему персональных заметок (аналог Evernote) с end-to-end шифрованием:

1. **Desktop** — Windows 10/11, нативное GUI-приложение.
2. **Mobile** — Android + iOS.
3. **Server** — опциональный домашний сервер синхронизации: **один статический бинарник**, запускаемый на домашнем ПК, NAS или Raspberry Pi.

Сервер — не центр системы, а необязательный транспорт. Клиент — самодостаточное приложение.

## 3. Жёсткие требования (не подлежат пересмотру)

| # | Требование |
|---|---|
| R1 | **Приложение полностью работоспособно без сервера.** Установка, создание учётной записи, все функции, бэкапы и восстановление доступны в режиме local-only. Сервер подключается позже, без миграции и потери данных. |
| R2 | End-to-end шифрование. Сервер **никогда** не получает открытый текст, ключи или пароль. Кража диска сервера не даёт доступа к содержимому. |
| R3 | Транспорт — TLS 1.3 поверх уже зашифрованного полезного груза (двойной контур). |
| R4 | Каждый клиент хранит **полную локальную копию** всех данных и полностью работоспособен offline. |
| R5 | Локальная история бэкапов за последние **7 дней** с восстановлением из UI и проверкой целостности. |
| R6 | Локальное хранилище зашифровано на диске; ключ защищён OS keystore (DPAPI/Windows Hello, Android Keystore, iOS Keychain/Secure Enclave). |
| R7 | Синхронизация конфликтоустойчивая: offline-правки на нескольких устройствах сходятся без потери данных. Merge только на клиенте — сервер не способен читать данные. |
| R8 | Полнотекстовый поиск — только локальный, по расшифрованным данным. Серверного поиска нет. |
| R9 | **Никакой внешней инфраструктуры**: ни PostgreSQL, ни S3/MinIO, ни Redis, ни очередей, ни Kubernetes. Сервер = один бинарник + один каталог с данными. |

## 4. Зафиксированная архитектура

Реализуй именно это. Отклонение — только при технической невозможности, с обоснованием в `docs/adr/`.

### 4.1 Разделяемое ядро

Ядро (крипто, локальное хранилище, sync-движок, модель данных) пишется **один раз на Go** и переиспользуется всеми модулями:

- **Windows desktop**: Wails v2 (Go-бэкенд + web-UI на TypeScript/React), сборка в один `.exe`, установщик NSIS.
- **Mobile**: то же Go-ядро через `gomobile bind` (AAR / XCFramework), UI на Flutter, связка через platform channels.
- **Server**: Go, `net/http` + chi. Никакого gRPC.

### 4.2 Хранилища

**Клиент:**
- SQLite (WAL) + SQLCipher (AES-256) — заметки, метаданные, лог операций, FTS5-индекс.
- Вложения — файлы на диске, зашифрованные, content-addressed: `blobs/<aa>/<bb>/<hash>`.

**Сервер:**
- **SQLite** (WAL, `busy_timeout=5000`, `synchronous=NORMAL`), драйвер `modernc.org/sqlite` — чистый Go, без cgo, кросс-компиляция под Windows/Linux/ARM одной командой.
- Вложения — **обычный локальный каталог**, та же content-addressed раскладка `blobs/<aa>/<bb>/<hash>`. Никакого объектного хранилища.
- Push-уведомления — WebSocket + in-process pub/sub на Go-каналах. Никакого Redis.
- Всё состояние сервера = `beresta.db` + `blobs/` + `config.yaml` в одном каталоге данных. Бэкап сервера = копирование этого каталога.

SQLite на 5 пользователях и десятках тысяч операций — запас на два порядка. Единственный писатель, сериализованные транзакции, никаких проблем с конкурентностью при таком профиле.

### 4.3 Криптографический дизайн

Примитивы — libsodium-совместимые (`golang.org/x/crypto`). Своих не изобретать.

```
Passphrase
  └─ Argon2id(salt, m=128MiB, t=3, p=4) ─> Root Key (32B)
       └─ HKDF(info="keybag") ─> Keybag Key

Keybag (шифруется Keybag Key; хранится локально, копия на сервере как непрозрачный блоб):
  ├─ Identity Key Pair (X25519)      — адресация ключей на пользователя
  ├─ Signing Key Pair (Ed25519)      — подпись операций и аутентификация устройства
  └─ Workspace Keys[] (32B)          — по одному на блокнот/workspace

Контент:
  note/blob ─> XChaCha20-Poly1305(key = HKDF(WorkspaceKey, info=object_id), nonce = 24B random)
  AAD = {schema_version, workspace_id, object_type}

Шаринг между пользователями:
  WorkspaceKey ─> crypto_box_seal(recipient X25519 pub) ─> key envelope
```

Правила:

- Параметры Argon2id **калибруются на устройстве при первом запуске** (целевое время ~1 с) и сохраняются рядом с шифротекстом. 256 MiB на мобильных вызывает OOM — верхняя граница 128 MiB.
- Пароль и Root Key никогда не покидают устройство.
- **Аутентификация на сервере — Ed25519 challenge-response ключом устройства. OPAQUE/SRP не нужны: пароль на сервер не отправляется в принципе.** `GET /v1/auth/challenge` → подпись nonce → сессионный токен (TTL 24 ч, refresh по тому же ключу).
- Регистрация на сервере — по **одноразовому invite-коду**, который генерирует владелец сервера (CLI: `beresta-server invite --user iurii`). Открытой регистрации нет. Это и есть модель доступа для 2–5 человек — списки, роли и RBAC не реализуются.
- Добавление второго устройства: (а) passphrase → скачать и расшифровать keybag с сервера; (б) **QR-pairing напрямую между устройствами по локальной сети** (SPAKE2 по короткому коду) — работает и без сервера.
- TLS для домашней сети: сервер при первом запуске генерирует самоподписанный сертификат; клиент **пинит его отпечаток при первом подключении** (отпечаток вшит в QR-код подключения). Опционально — Let's Encrypt, если сервер выставлен наружу.
- Отзыв устройства/участника → ротация WorkspaceKey и перешифровка envelope'ов. Ранее скачанные им данные вернуть невозможно — **это документируется в `docs/threat-model.md` явно, не маскируется**.
- Дедупликация вложений — по `HMAC(BlobKey, plaintext)`, не по «голому» SHA-256.

### 4.4 Модель синхронизации

Append-only лог операций на workspace. Транспорт абстрагирован:

```go
type SyncTransport interface {
    Push(ctx, workspaceID, []Op) error
    Pull(ctx, workspaceID, cursor) ([]Op, Cursor, error)
    PutBlob / GetBlob
    Subscribe(ctx, workspaceID) (<-chan Cursor, error)
}
```

Реализации:

1. **`local`** — no-op транспорт. Режим по умолчанию при первом запуске: работает всё, кроме синхронизации между устройствами. **Обязательная реализация.**
2. **`http`** — домашний сервер Beresta Sync. Обязательная.
3. **`folder`** — опциональная (фаза 8): лог операций пишется в общий каталог (USB-накопитель, сетевая шара, сторонняя папко-синхронизация). Операции уже зашифрованы и append-only, поэтому дополнительной крипто-работы не требуется — только файловая нарезка и защита от гонок через lock-файл. Даёт синхронизацию двух домашних машин вообще без сервера.

Механика:

- Тело заметки — CRDT (**Yjs**-совместимая структура или Automerge; выбери одну, обоснуй в ADR): одновременное редактирование сходится без конфликт-копий.
- Метаданные (заголовок, теги, блокнот, флаги) — LWW-Register с Hybrid Logical Clock.
- Удаление — tombstone, сборка мусора через 30 дней.
- Операция: `{op_id: UUIDv7, workspace_id, seq (назначает сервер), device_id, hlc, key_id, nonce, ciphertext, sig}`.
- Сервер видит только `workspace_id`, `device_id`, `seq`, размер, время. `note_id`, тип операции и содержимое — внутри шифротекста.
- Клиент: `pull(cursor)` → apply → `push(pending)`, идемпотентность по `op_id`, exponential backoff, WebSocket-нотификация о новом `seq`.
- Компакция: клиент периодически публикует зашифрованный снапшот состояния workspace, сервер обрезает лог до снапшота. Для 5 пользователей это одна фоновая задача, без шедулеров и брокеров.
- Вложения: chunk 4 MiB, шифрование пофрагментно, resumable upload/download, ленивая загрузка на mobile.

### 4.5 Бэкапы и версионирование (R5)

**На каждом клиенте** — работает в том числе в режиме local-only, это основной механизм сохранности данных при отсутствии сервера:

- Ежедневный снапшот: `VACUUM INTO` → zstd → XChaCha20-Poly1305, имя `backup-YYYYMMDD-HHmmss.enc`, отдельный каталог. Ротация — **7 последних суточных**. Пропущенный (устройство было выключено) — снапшот при первом запуске.
- Внеочередной снапшот перед восстановлением и перед миграцией схемы — вне квоты 7.
- Целостность: SHA-256 манифест, проверка при старте; повреждённый архив помечается и не участвует в ротации.
- UI: список бэкапов (дата, размер, число заметок), предпросмотр, восстановление целиком либо выборочно, dry-run.
- Настраиваемый внешний каталог бэкапов (второй диск, сетевая шара, съёмный носитель) — для local-only это критично.
- **Версии заметок**: локальная история ревизий за 7 дней, diff и откат, хранение дельтами.
- Экспорт: полный дамп в открытом виде (Markdown + вложения + `manifest.json`) по явному подтверждению пользователя. Импорт того же формата + импорт из Evernote `.enex`.

**На сервере** — ежедневный снапшот `beresta.db` (`VACUUM INTO`) + hardlink-снимок `blobs/`, ротация 7 суток, CLI `beresta-server backup|restore|verify`.

В CI — тест «сделать бэкап → уничтожить БД → восстановить → сверить хеши всех заметок и вложений».

## 5. Модули: объём работ

### 5.1 Server (опциональный)

- Один статический бинарник, без зависимостей от рантайма. Кросс-компиляция: `windows/amd64`, `linux/amd64`, `linux/arm64` (Raspberry Pi).
- Запуск: `beresta-server --data ./data`. Конфиг — `config.yaml` с дефолтами, работает и без него.
- CLI: `invite`, `users list`, `device revoke`, `backup`, `restore`, `verify`, `gc`.
- HTTP API `/v1`: `auth/{challenge,verify,refresh}`, `register` (по invite-коду), `devices` (list/revoke), `keybag` (get/put с CAS по версии), `workspaces` + `members` + `key-envelopes`, `sync/ops`, `sync/changes?cursor=`, `sync/stream` (WS), `blobs` (init/chunk/complete/get), `snapshots`, `healthz`.
- Схема SQLite: `users, devices, workspaces, memberships, key_envelopes, ops, blobs, blob_refs, snapshots`. Миграции — встроенные, `embed.FS` + goose. Индексы: `ops(workspace_id, seq)`, `blob_refs(blob_hash)`.
- Ограничения: размер операции, размер блоба, суммарная квота на пользователя, простой лимит частоты запросов в памяти. Проверка Ed25519-подписи операции против зарегистрированного ключа устройства, защита от replay (`op_id` + окно HLC).
- Обязательные проверки авторизации на каждом запросе + тесты на IDOR (5 пользователей не отменяют изоляцию).
- Логи структурные, без содержимого и ключей. Метрики — опционально `/metrics`, не обязательны.
- Деплой: скачал бинарник → запустил. Дополнительно: unit для systemd, `.bat` + задание планировщика для Windows, минимальный Dockerfile (опция, не основной путь).

### 5.2 Desktop (Windows)

- Дерево блокнотов, теги, список заметок, редактор (Markdown + WYSIWYG), вложения drag&drop, вставка изображений из буфера.
- Мгновенный локальный поиск (FTS5), фильтры по тегам/датам, сохранённые запросы.
- Глобальный хоткей «быстрая заметка», трей, автозапуск.
- **Онбординг с двумя ветками: «Только на этом компьютере» и «Подключиться к серверу» (URL + invite-код или QR).** Первая ветка — путь по умолчанию, к серверу можно вернуться в любой момент из настроек.
- Индикатор состояния синхронизации (включая явное «синхронизация выключена»), журнал конфликтов, менеджер устройств, экран бэкапов.
- Блокировка по таймауту, разблокировка Windows Hello, wipe локальных данных при отзыве устройства.
- Установщик + автообновление с проверкой подписи.

### 5.3 Mobile

- Тот же функционал: список/редактор, offline-first, фоновая синхронизация (WorkManager / BGTaskScheduler).
- Режим без сервера: локальные заметки + бэкапы в каталог устройства/облачный диск + обмен с десктопом через QR-pairing по локальной сети.
- Биометрическая разблокировка, авто-lock, скрытие содержимого в task switcher.
- Share extension (текст/фото/ссылка из других приложений), быстрая заметка из виджета.
- Настройка «держать вложения offline» (все / избранные блокноты / только метаданные), лимит кэша.
- Локальные бэкапы по тем же правилам, с учётом свободного места и предупреждением при нехватке.

## 6. Нефункциональные требования

Целевой масштаб — **до 5 пользователей, до 20 000 заметок и 20 ГБ вложений на пользователя.** Не проектируй под большее: горизонтального масштабирования, шардирования и партиционирования быть не должно.

- Cold start desktop ≤ 1.5 с при 20k заметок; локальный поиск ≤ 150 мс.
- Инкрементальная синхронизация 1000 операций ≤ 3 с в локальной сети.
- Потребление сервера в покое: ≤ 50 МБ RSS, near-zero CPU. Должен незаметно жить на Raspberry Pi.
- Корректность при `kill -9` в любой момент: транзакционность, отсутствие частично применённых операций, WAL-recovery.
- Покрытие тестами ядра ≥ 80%: unit (крипто-векторы, CRDT-конвергенция), property-based на sync (случайные перестановки операций → идентичное состояние), интеграционные, e2e (два клиента + сервер: offline, конфликт, отзыв устройства) **и отдельный e2e без сервера вообще**.
- Безопасность: zeroization ключей в памяти, отсутствие секретов в логах и crash-репортах, запрет скриншотов на защищённых экранах mobile, пиннинг сертификата, `govulncheck` + `osv-scanner` в CI.
- Локализация ru/en с первого коммита.

## 8. Порядок выполнения

Каждая фаза завершается компилируемым и протестированным кодом.

1. `docs/`: архитектура, threat model (STRIDE), крипто-спецификация, спецификация протокола синхронизации, ADR по CRDT и по стеку клиентов.
2. `core`: crypto-слой + тестовые векторы; локальное зашифрованное хранилище + миграции; модель данных.
3. `core`: транспорт `local` + бэкапы + история ревизий. **К концу фазы система полностью работоспособна без сервера.**
4. `desktop`: полный UI в режиме local-only.
5. `server`: SQLite-схема, auth по ключу устройства, invite-коды, sync-лог, блобы, WS, CLI; интеграционные тесты.
6. `core`: транспорт `http`, sync-движок, CRDT, конфликты, снапшоты; property-тесты. Подключение сервера в desktop.
7. `mobile`: полный UI, QR-pairing, фоновая синхронизация.
8. Шаринг между пользователями, ротация ключей, отзыв. Опциональный транспорт `folder`. E2E-сценарии, документация, релизная сборка.

## 9. Правила работы

- **Не задавай уточняющих вопросов.** Недостающие решения принимай сам, фиксируй в `docs/adr/` и `ASSUMPTIONS.md`.
- Выдавай законченный компилируемый код с обработкой ошибок; никаких `TODO`, заглушек и `panic("not implemented")` в сдаваемых фазах.
- **Простота — требование, а не пожелание.** Любую абстракцию, оправданную только гипотетическим ростом нагрузки, не вводить. Пять пользователей — это потолок.
- Комментарии по существу, на английском; пользовательские строки — через i18n.
- В конце каждой фазы: список созданных файлов, команды сборки и запуска, что покрыто тестами, известные ограничения.
- Любое отклонение от разделов 3–4 явно помечай и обосновывай.

## 10. Критерии приёмки

- [ ] Приложение устанавливается и полноценно работает на машине, где сервера не существует: заметки, вложения, поиск, бэкапы, восстановление, экспорт.
- [ ] Сервер, подключённый спустя время к уже наполненной базе, синхронизирует её без потерь и без ручной миграции; отключение сервера возвращает приложение в рабочий local-only режим.
- [ ] Каталог данных сервера (`beresta.db` + `blobs/`) не позволяет восстановить ни одной заметки без пароля пользователя.
- [ ] Пароль и производные ключи отсутствуют в трафике (проверяется mitm-прокси) и в логах сервера.
- [ ] Правки одной заметки на двух устройствах в offline после синхронизации сходятся, ни один абзац не потерян.
- [ ] Отзыв устройства делает недоступными последующие операции для его ключа; ротация проходит без простоя.
- [ ] Восстановление из бэкапа семидневной давности даёт согласованное состояние; ротация оставляет ровно 7 суточных архивов.
- [ ] `kill -9` во время синхронизации не приводит к порче БД и дублированию операций.
- [ ] Сервер запускается на Raspberry Pi командой из одной строки и работает без внешних сервисов.
- [ ] Сборка с нуля на чистой машине по `README.md` проходит для всех трёх модулей.
